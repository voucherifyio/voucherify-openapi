The `EVALUATION_REFRESHED` event indicates that a Loyalty v2 tier evaluation changed without changing the member's tier or the calendar day of the tier expiration.

<Note>
This page documents only the event data nested under `data`. See [Introduction to webhooks](/api-reference/introduction-to-webhooks) for the shared webhook structure, and [Workflows webhooks](/api-reference/workflows-webhooks) for the full Workflows webhook payload.
</Note>

This event can trigger a workflow when **Loyalty transaction** is configured with the **Tier transactions** group and the `EVALUATION_REFRESHED` transaction type. If the workflow reaches a **Webhook callout** action, Voucherify sends a webhook to the action's target URL.

Workflows send this transaction in the `data.trigger` object. The example uses the `APPROVED` status. A workflow can filter the trigger by transaction status: `PENDING`, `APPROVED`, or `REJECTED`. The matched status is available in `data.trigger.transaction.status`; it does not create a separate event type.

Voucherify creates this transaction when the member stays in the same tier, the expiration day does not change, and the stored tier evaluation differs:
- Points change inside the current tier, or a future period in the evaluation changes.
- A point-earned tier structure uses `NEXT_TRACKING_PERIOD` and records a join or an upgrade that starts in a later period. The tier does not change yet.
- `NO_DOWNGRADE`, or `SINGLE_LEVEL` after the one allowed drop in the current cycle, keeps the member in the current tier when the points would otherwise move the member further down or out of the tier structure.

A tier change is a `JOINED`, `UPGRADED`, `DOWNGRADED`, or `LEFT` transaction. A change of the expiration day is an `EXPIRATION_CHANGED` transaction.

`details.tier_from`, `details.tier_to`, and `details.start_at` are `null`. `transaction.tier_id` is `null`. The current tier stays on the member's tier record and is not copied onto this transaction.
